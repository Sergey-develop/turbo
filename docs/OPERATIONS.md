# Запуск и production

## Локальный запуск

Node.js >=22.13, Git, npm. На Windows команды выполняйте из `C:\Users\sprin\Desktop\турбопушка\landing`.

```powershell
npm.cmd ci
npm.cmd run build
npm.cmd run db:migrate
npm.cmd run dev -- --port 5175
```

В среде Windows IDE может держать esbuild/rollup открытыми. Если `npm ci` сообщает EPERM, остановите свой dev-процесс либо используйте `npm install` с сохранённым package-lock.json; не удаляйте чужие процессы и файлы с блокировкой.

Откройте `http://127.0.0.1:5175/signin-with-chatgpt?return_to=/admin`. Предоставленный Sites mock-вход работает только на loopback, удаляет переданные пользователем identity headers и входит как seedy@sites.test. Локальные тестовые секрет и роль добавлены только при `vite serve`; production build их не содержит.

В Настройках нажмите «Инициализировать настройки и текущий контент». Это идемпотентная запись стартовых данных; схемы во время HTTP-запросов не создаются. Бизнес-режим остаётся closed. Для локального теста можно явно задать тестовые основания и тексты. Не переносите их в production.

После добавления миграций повторите build и db:migrate. Локальная и hosted D1 — разные базы. Применённые SQL-файлы и журнал миграций не изменяются.

## Проверки

```powershell
npm.cmd run typecheck
npm.cmd run lint
npm.cmd test
npm.cmd run build
# При запущенном локальном dev-сервере:
npm.cmd run test:browser
```

`test` использует настоящий SQLite и параллельные worker_threads с отдельными соединениями. `test:browser` создаёт только локальные тестовые записи и меняет локальные настройки/черновики; на production URL он отказывается работать. Windows использует установленный Chrome; путь можно задать CHROME_PATH. На других ОС установите Chromium командой `npx playwright install chromium`. Playwright нужен только для QA, в клиент не попадает.

## Переменные среды

Все значения задаются в серверных runtime settings Sites, а не в VITE_* и не в Git.

| Имя | Назначение |
| --- | --- |
| BOOTSTRAP_ADMIN_EMAILS | Проверенные платформой email начальных администраторов через запятую. Для production назначается текущий владелец сайта. |
| CANCEL_SECRET | Криптографически случайный постоянный секрет HMAC ссылок отмены. Смена сделает старые ссылки недействительными. |
| JOB_RUNNER_SECRET | Секрет вызова внутреннего обработчика очереди. |
| MAIL_PROVIDER | disabled либо resend. |
| RESEND_API_KEY | Секрет провайдера. |
| MAIL_FROM | Адрес отправителя с подтверждённого у провайдера домена. |
| PUBLIC_ORIGIN | Канонический HTTPS origin для ссылок в письмах; без пути и завершающего слэша. |
| DB, BUCKET | Автоматические bindings Sites для D1 и R2, не текстовые .env переменные. |

`.env.example` содержит только имена. Для локальных собственных значений используйте игнорируемый `.dev.vars`; фактические production секреты туда не копировать.

## Развёртывание

Проект остаётся привязан к `.openai/hosting.json` с существующим project_id. Публикуется через Sites source workflow, с сохранением приватного доступа. Сборка содержит `dist/server/index.js`, конфигурацию Worker, `dist/client` и metadata с миграциями. Sites создаёт DB/BUCKET и применяет hosted миграции перед выпуском Worker. Не используйте прямой `wrangler deploy` для этого сайта.

Порядок первого запуска production:

1. Проверить доступ владельца на `/admin` и инициализировать стартовый контент.
2. Заменить контент из макета на утверждённые программу, спикеров, фотографии и тексты.
3. Подтвердить территорию хранения D1/R2 и условия обработки ПДн. Задать тексты, основания, версии согласий и срок хранения.
4. Задать вместимость, лимит заявок и круг менеджеров. Сотрудникам нужен и доступ к самому приватному сайту, и роль в приложении; назначение роли не меняет audience Sites.
5. Подключить Resend и проверенный домен отправителя, проверить шаблоны, поставить тест себе, обработать очередь и проверить факт доставки у провайдера. Пока ключа нет, реальная доставка не проверена.
6. Настроить внешний защищённый планировщик для POST `/api/internal/mail/dispatch` раз в минуту; JSON `{}`, Authorization Bearer JOB_RUNNER_SECRET и отдельный platform service access приватного сайта. Контролировать failed/sending задания в кабинете. Планировщик пока не создан.
7. Выбрать open/moderated/waitlist и только после проверки legalApproved включить приём.

Тестовые письма отправляются только на email текущего администратора. API шаблонов не является произвольным почтовым реле.

## Резервные копии и восстановление

Локальная согласованная SQLite-копия: `npm run db:backup`; файлы в игнорируемой папке backups. Копия делается через SQLite VACUUM INTO, а не простым копированием открытой БД с WAL. Скрипт отказывается угадывать базу при нескольких локальных D1. Для проверки восстановления остановите локальный сервер и используйте **новую** папку состояния Miniflare; размещение восстановленного файла должен проверить разработчик по конфигурации локальной D1. Не заменяйте рабочую БД без отдельной сохранённой копии.

В кабинете «Хранение данных» доступен JSON-снимок семи таблиц D1. Чтения выполняются одним batch. Лимит — 10000 строк на таблицу; для большей БД нужен полный экспорт через оператора хостинга. Снимок содержит ПДн, храните его в защищённом хранилище с тем же утверждённым сроком хранения. R2-фотографии и runtime secrets в JSON не входят: их резервируют отдельно.

Производственное восстановление и point-in-time recovery выполняет уполномоченный оператор хостинга. Самостоятельного restore endpoint, который мог бы затереть рабочие заявки, нет. До открытия регистрации согласовать с оператором расписание резервирования, доступ, восстановление на отдельном окружении и срок хранения копий. Автоматические production backups в рамках приложения пока не настроены.

## Инциденты

При проблемах приёма перевести форму в closed: ранее принятые записи сохраняются. При проблемах почты выключить mailEnabled: очередь остаётся в БД. Не сбрасывать sending-задания вслепую; сверить их ключи с провайдером. Не удалять миграции после неуспешного deploy — БД могла успеть их применить. При конфликте версии в кабинете обновить данные, затем повторить изменение.
